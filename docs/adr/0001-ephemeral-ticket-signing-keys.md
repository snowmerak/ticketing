# ADR 0001: 인스턴스별 임시 Ed25519 대기표 서명키

- 날짜: 2026-09-24
- 상태: 채택·구현 (로컬 V1), 요청 시 회전·시작 등록 부분은 [ADR 0002](./0002-background-ticket-key-registration.md)로 대체
- 결정 권한: 프로젝트 사용자

## 배경

기존 HMAC-SHA-256 대기표는 모든 API 인스턴스가 같은 비밀키를 받아야 했다. 한 인스턴스가 비밀키를 노출하면 전체 인스턴스의 서명 권한이 영향을 받고, 키 교체 시 이미 발급된 대기표를 검증할 공유 구성이 없었다. 요구사항은 인스턴스가 자체 키를 만들고 공개 검증키를 별도 Redis에서 조회하게 하는 것이다.

## 결정

각 `serve` 인스턴스가 시작 시 메모리에서 Ed25519 키쌍을 생성한다. 공개키의 SHA-256 해시를 Base64 URL-safe로 표현한 값이 `kid`다. 별도 키 Redis에 공개키를 TTL과 함께 등록한 뒤에만 토큰 버전 2를 서명한다. 발급·갱신 시 현재 공개키의 등록 상태를 확인하고, 검증 시 토큰의 `kid`로 공개키를 조회한다. 서명 가능 기간이 지나면 다음 발급·갱신에서 새 키쌍을 먼저 등록한 뒤 전환한다. 개인키는 Redis·설정·로그에 보관하지 않는다.

키 Redis 구현은 [어댑터](../../internal/keyredis/registry.go)에 가두고 서명 로직은 [좁은 Registry 계약](../../internal/ticket/registry.go)에만 의존한다. 키 Redis가 불가하면 발급·검증·readiness는 닫힌다. 공개키 보존 TTL은 서명 가능 기간과 대기표 TTL에 1분 여유를 더한다. 등록 권한은 인프라 네트워크와 인증/ACL로 보호해야 하며 공개키 해시는 등록자의 신원을 증명하지 않는다.

## 대안과 영향

공유 HMAC 비밀키를 Redis에 올리는 방식은 대칭키 조회가 가능한 모든 검증 인스턴스에 서명 권한까지 주므로 채택하지 않았다. 기존 HMAC 키를 다중 버전으로 모든 프로세스에 주입하는 방식도 인스턴스별 키 분리를 충족하지 못한다.

티켓 버전 1과 2는 호환되지 않으며, 배포 전 미만료 버전 1 대기표의 만료 대기나 명시적 재발급 절차가 필요하다. 키 Redis는 새로운 가용성·신뢰 경계다. AOF/`noeviction`이어도 상태 손실·failover 무손실은 보장되지 않고, 과거 공개키 손실 시 이미 발급된 토큰은 검증할 수 없다. 긴급 폐기·자동 복구·운영 ACL 검증은 이 로컬 V1 범위 밖이다. 기존 벤치마크 수치는 새 Redis 조회 경로의 성능 증거가 아니다.

## 검증

서명·검증·회전·레지스트리 중단·동시 회전 단위 테스트, 실제 Redis의 공개키 TTL·손상 거부 통합 테스트, 실제 API 재시작 뒤 이전 인스턴스 대기표 검증 E2E를 사용한다. 실행 결과와 환경은 변경 시점의 테스트 기록 또는 작업 결과가 소유한다.
